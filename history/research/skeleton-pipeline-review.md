## 2. What is required to finalize ANY skeleton

These checklists distinguish existing requirements from proposed automation checks. They do not assert every gate was recorded for the historical deck.

### Must be true of the skeleton file itself

- One source post, source URL, fixed source slide count, ordered source images. Preserve source-to-deck index mapping when a captain-directed reorder occurs.
- Every slide defines Role, Text, Placement, Image and its style-digest link. Retain the README's section order: Structure, Slide count, Slide by slide, Hook, Images, Text style, Fixed vs open, Why it works, Porting, Source slideshow.
- The hook preserves the source wording as a slot template, with explicit slot types. Only hooks that actually address a demographic need demographic slots and bank-derived options; do not bolt “for beginners” onto every format.
- Mark text as rigid template, fixed verbatim, or open. Preserve unusual human/emotional lines exactly when their wording is the mechanism. Ordinary tips specify function and length, not conjunctions or sentence formulas. No invented fixed emotional line when a source has none.
- Keep the topic portable and the blueprint free of account names, product and CTA. Distinguish observable structure from hypotheses about saves/comments; the README explicitly forbids unsupported effects.
- Proposed implementation detail: resolve prose placement into caption regions, font styles, canvas ratios and image fit rules; reserve those same regions in the image plan. A photo zone may overlap an intentional torso area, but must not obscure required face/prop detail. This goes beyond the current skeleton prose.
- Proposed readiness gate: validate all linked digests and local source assets, record provenance, identify conflicts with house rules before calling the file production-ready. Source popularity alone is not proof that our version will work.

Basis: `sections/slideshows/skeletons/README.md`; `log/LOG.md` E154–E171, E201–E209, E226–E228. Do not universalize the joke's seven slides, heartbreak, lowercase or “anxious” rejection to unrelated source formats.

### Must be true of the deck built from it

- Account, topic and skeleton version are explicit; the account's approved references exist before character prompts are built. Read account overrides and character data anew after a recast.
- The script fills the hook slots and pays the promised count, retains fixed text, and preserves the slide roles and visual sequence. Captain-authored text remains exact, with any departure from a generic range recorded rather than silently normalized.
- A written script review and captain review precede generation under the current workflow. A historical permission to reuse a script is attached to that deck, not treated as blanket permission to bypass review.
- Every image prompt passes `core/skills/image-prompt/check.py check` with `sections/slideshows/image-rules.json`. References distinguish identity/physique/props from style; style-only digests are not image attachments. No person on the food slide means no character-reference requirements there.
- Models/settings and paid work follow the authorized scope. A successful request, a valid JSON, an image PASS and a captain approval are separate statuses.
- Review each image at full resolution and in enlarged crops for identity, physique, anatomy, hands, reflections, props, style, place and caption space. Save per-image verdicts and precise fixes. Follow the current same-session review instruction; resolve contradictory older reviewer-session wording before automation.
- Overlay the exact approved script only on reviewed images; check wrapping, contrast, crop, placement and final dimensions. The final captioned artifact needs its own inspection and captain approval. Posting is a separate action.

Basis: `sections/slideshows/workflows/make-slideshow.md`, `core/skills/image-prompt/SKILL.md`, `core/skills/review-images/SKILL.md`, Zoey's saved review, and `log/LOG.md` E237–E240, E254–E265, E269–E273. Hayden's final approval is recorded; a complete Hayden per-crop written PASS trail is not established by those entries.

## 5. Automation design

### What the existing scratch scripts teach

Both `raw/zoey-06/prepare-prompts.py` and `raw/hayden-06/prepare-prompts.py` hard-code seven scenes, the reordered digest list, account descriptions and special cases such as `i == 3` for food and `i == 4` for the face selfie. Neither reads the approved script to derive captions or reads a machine-readable skeleton. They copy core example JSONs, fill photographic fields from digests, construct reference manifests and reserve caption space. That mapping is reusable; the deck-specific literals are not.

Hayden's current builder still has honey-blonde scene strings alongside espresso-brown identity fields, plus an intent string saying no case is chosen while continuity specifies a black silicone case. These are concrete stale-data hazards in the code as read, not a claim that every final image has those defects. Rerunning this builder is not proven to reproduce the historically approved prompts.

The two `run-nano-group.py` files use concurrent ordinary `generateContent` calls, not a vendor asynchronous Batch API. Zoey's runner selects six character slides; Hayden's selects all seven. They hard-code model, 512 size, 9:16 and `v1` paths, attach manifest images, and save usage metadata. Re-execution can overwrite outputs and spend again; there is no durable per-job resume contract.

`raw/hayden-06/overlay.py` hard-codes captions and JPEG paths, center-crops to 1080×1920, uses local font fallbacks and only top/lower placement. It computes block height without enforcing bounds. It cannot directly express Notes sections, Do/Don't stacks, 4:5 counters or a 3:4 image inside bars.

### Proposed schema and ownership

Add tracked `sections/slideshows/schemas/skeleton.schema.json`, with instances at `sections/slideshows/skeletons/<slug>.json`. Proposed contract `slideshow-skeleton/1` contains `id`, `version`, `source`, `slide_count`, defaults and ordered `slides`. Every slide has stable ID, `source_slide_index`, `role`, `text_blocks`, `placement`, `image`, and `digest`. Each text block chooses exactly one level: `template` (literal frame plus typed slots), `verbatim` (exact text), or `open` (role and length). Number prefixes, counters and repeated labels are separate from content so word counting is deterministic.

Use `image.kind = character_photo | object_photo | text_card | existing_asset`, with explicit `person_visible`, `body_visible`, `phone_visible`, scene constraints and source aspect ratio. `placement` supplies normalized text rectangles, alignment, font/style IDs, safe zones and reserved image space; support multiple blocks. Record both content aspect ratio and output canvas, plus `contain`, `cover` or `letterbox` and a crop anchor. Digests remain non-identifying records in `library/styles/`; account identity remains solely in account-owned files.

This is the schema change that lets one builder serve every skeleton: typed slide content plus arbitrary ordered slides and text blocks, instead of seven positional branches and a single caption. Do not add slideshow-specific fields to the universal `organic-image-prompt/1` schema: use a slideshow job envelope with an existing organic prompt payload only for generated-photo jobs. A text card has a deterministic render payload and no paid image prompt.

Make JSON the canonical executable skeleton and render its human-readable Markdown, including explanations/source gallery, from the same record after migration. Avoid two independently maintained rule copies. During migration, compare JSON against the existing Markdown before accepting it. Account-specific configurations and fixtures live under `sections/slideshows/accounts/<name>/`, never in shared builders or skeletons.
